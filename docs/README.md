## 📐 معايير وقواعد نظام التوثيق (Documentation Standards)

للحفاظ على نظافة التوثيق وسهولة تصفحه والتعامل معه بواسطة المطورين ونماذج الذكاء الاصطناعي، نتبع القواعد التالية:

1. **مبدأ المصدر الوحيد للحقيقة (SSOT):**
   - أي قرار تقني أو بعد تصميمي (مثل مقاس الجزيرة، تكلفة الطريق، أبعاد المبنى) يجب توثيقه في ملفه المخصص، ويُمنع تكرار المعلومة بتفاصيل متناقضة في مكانين.

2. **قاعدة التقسيم التدريجي (Progressive Modularization):**
   - **الملف الموحد:** يبدأ أي موضوع فرعي كملف أو قسم ملخص ضمن مجلده.
   - **حد الانقسام (~150 - 200 سطر):** إذا تجاوز الملف هذا الحد أو تشعبت مواضيعه، يُقسّم فوراً إلى مجلد مخصص يحتوي على:
     - `index.md`: ملف الفهرس الملخص للموضوع مع جداول سريعة وروابط.
     - `sub-topic.md`: ملفات تفصيلية مستقلة لكل جانب فرعي (مثل: `terrain.md`، `ocean.md`، `biomes.md`).

3. **هيكل الملف القياسي (Standard File Layout):**
   - كل ملف فرعي يجب أن يبدأ برابط رجوع للمستوى الأعلى: `[← العودة إلى الفهرس](index.md)`.
   - جدول ملخص بالثوابت والأرقام الرياضية في البداية (Summary Constants).
   - توضيح الكود المصدري المرتبط بالتوثيق (Code Link).

4. **⚠️ إلزامية توثيق كل تعديل في الخطط والأنظمة (Mandatory Plan & Change Logging):**
   - **قاعدة ذهبية:** يُمنع تعديل أي خطة عمل، نظام، خوارزمية، أو أبعاد تصميمية في الكود دون تحديث الملف المخصص لها في مجلد `docs/` في نفس الوقت.
   - **توثيق التغييرات (Changelog / Decision Records):** عند تعديل قرار سابق (مثل تعديل أبعاد المباني، تكاليف الطرق، أو آليات الاقتصاد)، يجب ذكر سبب التعديل وتأريخه في الملف المعني لضمان وضوح تسلسل القرارات.
   - **المزامنة بين الخطط والكود:** التوثيق هو المعيار والمصدر المرجعي الأول؛ الكود يتبع التوثيق والخطط دائماً وليس العكس.
